## Data flow

```
Enterprise Audit Log API  →  hourly cron + custom script  →  Share Link Audit Trail (new rows)
                                                            →  Share Links (status updated)
                                                            →  Config (last-check timestamp)
```

## The hourly run, step by step

**1. Read the last check time.** The script reads `Last Audit Check Time` from the single record in the `Config` table. If none exists yet, it defaults to 24 hours ago.

**2. Page through the Audit Log API.** It calls `GET /v0/meta/enterpriseAccounts/{enterpriseAccountId}/auditLogEvents`, filtered with four repeated `filterByEventTypes` params (`enableShare`, `disableShare`, `configureShare`, `regenerateShare`), `pageSize=100`, and follows the returned `offset` for up to 10 pages per run, with a 200ms pause between pages to stay easy on the API.

**3. Filter to genuinely new events.** Each page is filtered again client-side against the last check timestamp, since the API filters by event type but not by time directly in this flow.

**4. Group by share and calculate risk.** Events are grouped by `modelId` (the share's ID). For each share, the script checks whether a matching record already exists in `Share Links`:
- If it exists, the record's `Status`, `Last Modified`, `Last Event Type`, and `Change Count` are updated, and every event for that share becomes a new row in `Share Link Audit Trail`.
- If it doesn't exist, it's a share that wasn't in the original CSV backfill. A new `Share Links` record is created, and the new audit row is tagged with the note *"New share link not in original CSV"*, exactly the kind of drift a point-in-time backfill will always eventually show.

**5. Write back in batches of 50.** Airtable's API caps batch writes at 50 records per call, so updates, new share links, and new audit entries are each chunked and written in a loop.

**6. Update the checkpoint.** `Config.Last Audit Check Time` is set to the current run's timestamp, and `Last Run Status` is set to `Success` (or the run logs an error and leaves the checkpoint where it was, so a failed run doesn't silently skip events).

## Why `viewShare` is deliberately excluded

The four tracked event types all represent a change to how a share behaves: turning it on or off, reconfiguring its restrictions, or rotating its ID. `viewShare` (someone simply opening a share link) doesn't change risk at all, it's usage, not configuration, and including it would have flooded the audit trail with noise that has nothing to do with what a security reviewer actually needs to see.
